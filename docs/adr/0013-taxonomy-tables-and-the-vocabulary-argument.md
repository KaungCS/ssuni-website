# Taxonomy terms are rows, and the vocabulary reaches pure code as an argument

ADR 0011 staged the enforcement of the declared taxonomy: `CHECK` constraints now, real tables next. This is the "next", decided by grilling on 2026-09-09 for issue #49 (which supersedes the earlier #38). It settles the choices 0011 explicitly deferred and several it did not anticipate.

**Collections get a join table, not a trigger.** `products.collections` is `text[]`, which has no natural foreign key, and 0011 named the two candidates without picking. A trigger checking every array element against `collections` would fire on writes to `products` — so it cannot stop the client **deleting a Collection row that Products still reference**, leaving slugs pointing at nothing. That is exactly the silent-invisibility failure this issue exists to eliminate, reintroduced one table over. A `product_collections` join table gets `on delete restrict` for free, and is the shape the Admin Dashboard's editor needs anyway. The cost is real: `products.collections` is dropped, `catalog_facets` stops using `unnest`, and the array data is backfilled into rows.

**Display labels move into the rows too, not just the slugs.** Leaving labels in `lib/taxonomy.ts` while slugs live in Postgres was the smaller change and was rejected: the client could then add a Category that renders under its raw slug until someone deploys. ADR 0007 makes the category editor the reason these tables exist, and an editor that cannot edit the display name is not one. `lib/taxonomy.ts` keeps its types and loses its vocabulary.

**`parseCatalogFilters` stays pure and synchronous; the vocabulary arrives as an argument.** Validation needs data that now lives in the database, and the tempting fix is to make the parser `async` and let it query. That would dissolve the seam `lib/catalog-url.ts` was split out to protect. Instead the page loads the taxonomy and passes it in — the same move `lib/cart.ts` already makes with availability, and for the same reason: every rule about what a URL means stays testable without a database. Codegen (regenerating `lib/taxonomy.ts` from the schema, like `lib/database.types.ts`) was rejected because it makes adding a Category require a deploy, a worse regression than the migration-per-Category one 0011 accepted as temporary.

**Because the page holds the vocabulary anyway, labels reach components as props rather than through a join.** The Product query is not touched: `CATALOG_SELECT` and its `variants_available` embed are load-bearing and stay exactly as they are. `getCatalogFacets()` is replaced by a single `getCatalogTaxonomy()` returning every declared term with its label, sort order, and whether any visible Product currently carries it — one round trip serving the parser, the drawer, and eventually the nav, instead of two overlapping reads of thirteen rows.

**Ordering is a `sort_order` column.** Declaration order in TypeScript was the authority for how the drawer read; with the lists gone, without an explicit column the drawer would fall to alphabetical or insertion order and stop matching the merchandised order in the header.

**There is no `is_active` flag.** Retiring a term means reassigning its Products and deleting the row, which `on delete restrict` makes loud. A term that exists but does not render is precisely the failure class being eliminated, and a Product filed under an inactive Category would 404 exactly like a typo'd one does today. Revisit only if the client asks.

## Consequences

**The vocabulary still lives in three places until a follow-up ticket lands.** `components/ShopDropdown.tsx` hardcodes all thirteen links with their display labels as literal JSX — a third copy neither ADR 0011 nor CLAUDE.md mentions. So a Category the client adds will filter correctly and appear in the drawer while being **absent from the navigation**, which is most of how anyone finds it. Making the mega menu read the taxonomy tables is deliberately a separate ticket, filed alongside this work rather than remembered; until it lands, "#49 removed the duplication" is only two thirds true. That ticket is #51. The nav must read the declared tables and not the facets, or a Department with no live Products vanishes from the header.

**The schema change ships as one migration, and there is a window where the live catalog 500s.** Expand–contract exists for changes whose blast radius fans across many call sites; here `products.collections` has exactly two readers, `lib/catalog.ts` and the `catalog_facets` view. But the database is migrated from a laptop (`npm run db:push`) while code deploys from a push to `main`, so between those two events one side is ahead of the other and catalog requests fail. Accepted because the site is pre-launch with no traffic and no domain; it would not be acceptable in October, and a later schema change of this shape should expect to pay for expand–contract. The migration backfills `product_collections` before dropping the column and `raise exception`s if the row count does not match the array elements it read, so membership cannot be silently lost — the client adds Products between sessions, and the seed data is not all that is there.
