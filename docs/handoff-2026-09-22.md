## What landed

Three fixes, all found by Kaung using the dashboard rather than by planning. Each was brainstormed
(`superpowers:brainstorming`, bounded path) and built under `ponytail`.

| Thing | Why it existed | Files |
|---|---|---|
| Admin clicking **Profile** now lands on `/admin` | `/profile` was the only nav route into the account area, and for an admin it showed an Order history they will never have | `app/profile/page.tsx`, `lib/admin.ts` |
| **Sign out**, on `/profile`, `/login` and the dashboard header | Nothing in the app had ever called `supabase.auth.signOut()`. Switching accounts meant waiting for the refresh token to expire | `lib/auth-actions.ts`, `components/LoginForm.tsx`, `app/login/page.tsx`, +2 |
| **Hidden Products marked** in the catalog | An admin is served Hidden Products by policy, and nothing said so | `lib/catalog.ts`, `components/ProductGrid.tsx`, `components/ProductDetail.tsx` |

Three things in there are worth not re-deriving:

**`isAdmin()` was extracted from `requireAdmin()`, not copied.** `lib/admin.ts` now exports both;
`requireAdmin()` calls `isAdmin()`. A second copy of the `admins` lookup in `/profile` is how two
surfaces come to disagree about who is an admin.

**The Hidden badge does no admin check, deliberately.** `products_select_public` is
`using (not is_hidden or is_admin())`, so a row arriving in the grid with `is_hidden` set has
already proved who is asking. `CatalogProduct.isHidden` is therefore sufficient on its own — no
session read, nothing to drift from the policy. Selecting the column is **not** the client-side
`is_hidden` filter `lib/catalog.ts` forbids: the database still decides who sees the row.

**The detail page needed the badge more than the grid did.** `variants_available` ends in
`where not p.is_hidden` and has **no admin exception**, so a Hidden Product's detail page renders
with its colour and size pickers empty. Unexplained, it reads as a broken storefront rather than a
hidden Product. The notice on that page says so and links to `/admin/products`.

### Why sign-out is a Server Action and not `POST /logout`

Two reasons, both load-bearing, both easy to undo by accident:

1. **It is the only kind of render that can clear the cookie.** `lib/supabase/server.ts` swallows
   cookie writes — a Server Component is already streaming by the time a query runs. In a Server
   Action the write lands. Move this into a page render and sign-out silently stops working while
   still appearing to.
2. **Server Actions carry Next's origin check.** A bare POST handler does not, and a logout endpoint
   without one lets any page on the internet sign our customers out with a hidden form.

It takes no parameters and always redirects to `/login`. A `?next=` read from the form body would be
an open redirect on a public POST endpoint — the same trap `components/LoginForm.tsx` guards on the
way in.

Verified under **workerd** via `cf:preview`, not just `next dev`: a Server Action writing cookies is
exactly the class of thing that passes one and fails the other.

### `/login` is no longer a static page

`app/login/page.tsx` is now a server component that reads the session and renders either
`components/LoginForm.tsx` (the OTP flow, moved unchanged) or a "Signed in as … / Sign out" panel.
It shows as `ƒ` rather than `○` in the build output. That is the whole cost and it was accepted
knowingly.

## What is NOT verified, and cannot be yet

**Every signed-in path in this session's work is untested by machine.** The sign-out forms and the
Hidden badges only render for a signed-in user or an admin, and no automated seam in this repo can
produce a Supabase session. What *was* verified end to end, signed out, on both `next dev` and
workerd: `/profile` and `/admin` redirect to `/login?next=…`, `/login` serves the OTP form, and

**A second account is impossible to test by hand until the domain exists (#27).** Resend will only

lets you switch accounts", and any UI check of `orders_select_own` against a stranger's Order,
cannot be confirmed manually. The RLS half of that *is* provable without email — `supabase/tests/
rls.mjs` drives raw anon clients — which is another reason #24 matters.

## Decisions taken this session

**Hidden Hero Stories will not get a badge.** They have the same gap on the home page that Products
had in the catalog, and it is deliberately unfixed: once the dashboard manages Hero Stories (step 4
of the plan), Hidden Stories will appear **only there** and stop rendering on `/` for admins at all.
A badge would be built to be deleted. When step 4 lands, change `getHeroStories()` to filter
`is_hidden` rather than leaving it to RLS, and update the docblock in `lib/hero.ts` that currently
documents the admin-sees-Archive behaviour.

**No public-view route in the dashboard.** It was considered and rejected: a private browser window
is a real anonymous request through real RLS, for free, and a hand-built preview is a second
rendering of the catalog that can drift from what shoppers actually get. `/admin/products` already
lists everything with its Hidden state.

**The Cart is untouched by signing out.** It lives in `localStorage` and belongs to the browser, not
the account. Emptying it on sign-out would be a surprise mid-purchase.

## What #24 turned out to be

Not what the plan assumed. `rls.mjs` already covered `hero_stories`,
`product_images` and the bucket, and `admin-path.sql` already covered `admins` —
so three of the four "new" things were done. What was genuinely missing was the
issue's own clause: *"with a second customer's session"*, which existed only as
`set request.jwt.claims` in SQL.

**That was believed to be blocked by the Resend single-address limit. It is
not.** The Auth admin API creates a confirmed user, the password grant returns a
real token, and the admin API deletes it — with **no email sent at any point**.
The limit blocks manual testing only, which is worth remembering the next time
something looks blocked on #27.

The suite now creates customer A, customer B and a temporary admin per run, and
proves the refusals on real tokens — including the ex-admin path, where removing
the allowlist row takes everything away from a token already issued.

## Four defects it found in already-merged code

All four surfaced for one reason: a Product was Hidden in the dashboard.

1. **Running the audit un-hid it.** Section 7 reverted `is_hidden` to `false`
   unconditionally rather than restoring the prior value.
2. A floor of 6 Variants and a hardcoded "rabbit-hole-hoodie costs 65" turned an
   ordinary Hidden Product into a red suite.
3. Sections 5, 9 and 11 picked a Variant by name or position, got one belonging
   to the Hidden Product, and failed five checks for nothing.
4. `admin-path.sql` aborted outright — it assumed its subject was not yet an

`/code-review` then found two problems in the new work, one of them serious: the
probe password was a **constant committed to git**, on accounts that are real,
confirmed, and briefly admin. Random per run now. And a failed sign-in painted
the whole section green, because `Bearer undefined` answers 401 and every
"customer cannot…" check accepts a 401.
