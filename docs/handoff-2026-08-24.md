## Verified, not assumed

The OpenNext bet in ADR 0005 was the biggest untested assumption in the plan, so it was tested rather than planned around:

- `@opennextjs/cloudflare@1.20.2` declares `next: ">=15.5.21 <16 || >=16.2.11"`; this app's 16.3.1 satisfies the second range. Installed with no peer conflicts.
- The adapter bundles a worker, and the worker serves `/`, `/catalog`, a dynamic product page, `/login`, and static assets through the ASSETS binding — all 200, real content, on the actual workerd runtime.
- `wrangler dev` picks up `.env.local` automatically, so `npm run cf:preview` gives good local parity.

Full detail is in the comment on issue #2. **Remaining work there is account-side only** — create the Cloudflare project and deploy.

## Findings worth not rediscovering

**Unknown product slugs return HTTP 200.** `/catalog/does-not-exist` renders a "Product Not Found" body with a success status, because the detail page is a client component rendering its own block instead of calling `notFound()`. Crawlers read the status, not the body, so dead product URLs would get indexed as real pages. Recorded on #25; fix during the server-component conversion in #9.

**Lint was buried 800:1.** A stray nested `ssuni-website/` directory held a 14MB `.next` build from a dev server once started a directory deeper. `.gitignore` anchored `/.next/` at the root and `eslint.config.mjs` ignored `.next/**` at the root, so neither caught it — `npm run lint` reported 4408 problems where the real source has 5. Both patterns are now unanchored. The same bug recurred within the hour when installing OpenNext created `.open-next/`, so: **any new build directory goes in both files.**
