## Things that will bite you if you don't know them

**The `admins` table is empty.** Admin writes are therefore denied to *everyone* right now. This is
not a bug and it is not a broken policy — it is an unmade authorization decision, left to the repo
owner. It will look like an RLS failure the first time #21 or #22 tries to write. To fix:

```sql
insert into public.admins (user_id) values ('c84f411b-aeab-4eee-bd69-75ce87539425');
```

**This project uses Supabase's current API keys, not the legacy `anon`/`service_role` JWTs.** It was
created after the cutover and legacy keys were never available on it. `.env.local` holds
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…`) and `SUPABASE_SECRET_KEY`
(`sb_secret_…`). Two gotchas: a secret key used from a browser is rejected with 401, and **neither
key type may be sent in an `Authorization: Bearer` header unless it exactly equals the `apikey`
header** — which will bite anyone hand-rolling a REST call in #15 or #18.

**`security_invoker = on` on `variants_available` is wrong, and looks right.** The availability
subquery reads `reservations`, which anon cannot; under invoker rights it matches zero rows and the
view reports full stock as available, overselling exactly the last unit ADR 0010 exists to protect.
Definer rights are confined to `private.variant_available_stock(uuid)`, which returns one integer.
There is a comment block in `20260825130000_shrink_definer_surface.sql` saying this; read it before
touching the view. `supabase db advisors` flagged the first design at ERROR level, which is how this
was caught — run it, don't assume.

**Read `variants_available`, never `variants.stock`,** on any surface that shows stock ("Few Left",
out-of-stock, size buttons). The raw count is what the client sees in Studio for restocking and is
deliberately a different number.

**The reservation check-and-hold does not exist yet.** The `reservations` table is there; the atomic
Postgres function that ADR 0010 requires is **not**. It belongs to #15. Do not read availability in
TypeScript and then insert — that reintroduces the race the ADR exists to close.

**`price` is `numeric(10,2)`, not integer cents.** Convert once at the Stripe boundary in #15:
`Math.round(price * 100)`.

**`collections` is `text[]`,** not the single column issue #3 described. Filter with
`collections @> '{best-sellers}'` (GIN indexed) in #10.

**Taxonomy columns hold slugs**, matching what `components/ShopDropdown.tsx` emits. Labels are in
`lib/taxonomy.ts` — use it in #9 rather than printing the raw slug. Note the nav still emits
`?filter=best-sellers` and `?filter=lookbook`; per the roadmap those become `?collection=` links in
#10, while `?filter=new` maps to `is_new`.

**Expected `db advisors` noise:** `rls_auto_enable` ×2 (a Supabase platform event trigger — it
returns `event_trigger`, so it is not actually RPC-callable despite what the warning says) and
leaked-password protection (moot: auth is email OTP, no passwords). **Anything else is a real
finding.**

**Still true from the 2026-08-24 handoff:** unknown product slugs return HTTP 200 with a "Product Not
Found" body, because the detail page is a client component rendering its own block instead of calling
`notFound()`. Fix during the server-component conversion in #9. And any new build/output directory
goes in **both** `.gitignore` and `eslint.config.mjs` — `npm run lint` must stay at 5 warnings, 0
errors.

## Environment a new machine will need

`.env.local` is not in the repo. It needs `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and `SUPABASE_SECRET_KEY`. `npm run db:push` and
`npm run db:verify` additionally need the CLI authenticated and linked:

```bash
npx supabase login --token sbp_…      # supabase.com/dashboard/account/tokens
npx supabase link --project-ref niynlwfnbgijsbovxgup
```
