# Weeks 5–6, Pulled Forward — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the remaining code-side launch scope — a real image gallery, and an Admin Dashboard the client can actually run the shop from — while the calendar still says week 4, so the last week is QA and the client track rather than feature work.

**Why now:** Decided 2026-09-19 by grilling (`/mattpocock-skills:grill-with-docs`). Weeks 1–4 finished early and `#22` (Hero Stories, week 5) already shipped. The binding constraint is no longer the calendar — it is the client-owned track (`#5`, `#6`, `#7`), none of which is addressed. Doing week 5–6 code now converts spare capacity into slack against those.

**Architecture:** No new services, no new dependencies. Product images become rows in a `product_images` table pointing at a Supabase Storage bucket. The Admin Dashboard is plain server components and server actions over the **existing** RLS policies — `products_admin_write`, `variants_admin_write`, `hero_stories_admin_write` and `orders_admin_all` already exist with their grants, so the admin needs no migrations of its own and, critically, **no new `lib/supabase/admin.ts` caller**.

## Global Constraints

- **The weeks 5–6 structural freeze binds the work, not the calendar.** Doing week-5 work in week 4 does not unfreeze week 4. New surfaces are additive and fine; restructuring `lib/cart.ts`, `lib/catalog.ts`, `lib/orders.ts`, `lib/stripe.ts` or either payment route is **out of scope**. `/improve-codebase-architecture` stays an October task.
- **The admin writes through RLS with the publishable key.** `lib/supabase/admin.ts` gains no new importer. If a task seems to need one, that is the signal to re-read the RLS policy, not to add the import.
- **No new dependencies.** Storage upload is `supabase-js`, already installed. Forms are server actions, built in. A new package means the npm 10 lockfile dance (CLAUDE.md) for no gain.
- **After every migration:** `npm run db:push`, then `npm run db:types`, then commit `lib/database.types.ts`. `npm run db:verify` green before the PR.
- **No test may assert an exact catalog row count.** Floors, runtime baselines, or the property itself.
- **`npm run lint` must end at 0 errors.** The 6 `<img>` warnings are `#11`'s and are expected to *drop* as this plan replaces them with `next/image`. Do not let the count rise.
- **Do not run `npm run build`, `npm run cf:build` or `npm run cf:preview` while `npm run dev` is running.** Confirm the dev server is down first.
- **TDD is not mandatory here.** CLAUDE.md scopes required TDD to Cart math, the reservation RPC, and webhook handling. None of this plan touches those. Tests are still required where logic is non-trivial — see each step.
- **One PR per numbered step.** Each must leave the store working and be independently mergeable. Kaung reviews and merges; do not merge on his behalf.

## Step 5 — RLS audit (#24) · hard gate · **runs first**

**It is smaller than this plan assumed.** `supabase/tests/rls.mjs` already carries §12 (Hero Stories) and §13 (`product_images` + the Storage bucket), and `supabase/tests/admin-path.sql` already covers `admins` / `admins_select_self` (lines 342–409). The 2026-09-22 handoff's claim that the audit "grew while nobody was auditing" is wrong on three of its four items.

What is genuinely missing is the clause #24 has always carried: *"with a second customer's session"*. Every customer-vs-customer check today is `set request.jwt.claims` inside `admin-path.sql`, which proves the **policy expression** and not the path — PostgREST parsing a real token, resolving a real role.

### The session helper

Verified working against this project on 2026-09-22: the Auth admin API creates a user with `email_confirm: true`, the password grant returns a real access token, and the admin API deletes the user afterwards. **No email is sent**, so the Resend single-address limit (#27) does not block any of this.

- [ ] Add a helper to `rls.mjs` that creates a user via `POST /auth/v1/admin/users` (secret key) and signs in via `POST /auth/v1/token?grant_type=password` (publishable key), returning a `req`-style caller bound to that token.
- [ ] Sweep `rls-probe-*@example.com` users at the **start** of the run, not only at the end. A crashed run otherwise leaks accounts into production auth — it did once, by hand, while designing this.
- [ ] Three identities: **customer A**, **customer B**, and a **temporary admin** (a real user with a row inserted into `admins` by the secret key).
- [ ] Delete all three at the end, and remove the `admins` row *before* deleting its user.

### What the real sessions must prove

- [ ] A reads their own Order; B's Order is invisible to A.
- [ ] A cannot reach B's Order Items **through the `orders → order_items` embed** — a different policy path from selecting `order_items` directly, and the one a leak would actually arrive on.
- [ ] A cannot `UPDATE` their own Order's `status` or `tracking_link`.
- [ ] A cannot select `admins` beyond their own (absent) row, and cannot select `reservations` at all.
- [ ] A cannot insert, update or delete `products`, `variants`, `product_images` or `hero_stories`.
- [ ] A cannot upload to the `product-images` bucket. Anon is already covered; **signed-in-but-not-admin is the likelier real attacker** and is the exact path `components/AdminImageUploader.tsx` takes in a customer's browser.
- [ ] The temporary admin *can*: see a Hidden Product, write the catalog, and move an Order's `status`.
- [ ] Removing the `admins` row takes all of that away again from the **same token** — nothing checks the ex-admin path today.

### The default-open sweep

- [ ] One query in `admin-path.sql` over `pg_class` / `pg_policies` that fails if any `public` table has RLS disabled or zero policies. It is the only assertion here that also covers tables that do not exist yet, including #49's.

### Closing it

- [ ] `npm run db:verify`, including the Supabase advisor. Expected findings are `rls_auto_enable` ×2 and leaked-password protection. **Anything else is real.**
- [ ] Record the run's output in a comment on #24 and close it. No `docs/` file: `rls.mjs` is the durable artifact, and a doc restating it is a second copy to drift.

**Verify:** `npm run db:verify` green · the suite leaves `auth.users` with exactly the real accounts it started with · every new check fails loudly if its policy is dropped (try it on one).

## Step 4 — Hero Stories CRUD

Mirrors `/admin/products` in shape, so the client learns one idiom: a list page plus an editor per row.

**Files**

| File | Responsibility |
|---|---|
| `lib/admin-hero.ts` (create) | Hero reads and writes for the dashboard, and the pure `reorderIds`. The `lib/admin-catalog.ts` of Hero Stories. |
| `app/admin/hero/page.tsx`, `app/admin/hero/[id]/page.tsx`, `app/admin/hero/actions.ts` (create) | List, editor, Server Actions. |
| `components/AdminImageUploader.tsx` (modify) | `pathPrefix` + `hiddenFields` in place of `productId` / `nextSortOrder`. |
| `components/ConfirmSubmitButton.tsx` (create) | ~10 lines, `"use client"`, `confirm()` on submit. |
| `lib/hero.ts` (modify) | `.eq("is_hidden", false)`, and the docblock rewritten. |
| `app/admin/layout.tsx` (modify) | One nav link. |

**Steps**

- [ ] `/admin/hero` lists every Story in `sort_order`, Hidden included, with a thumbnail, its Hidden state, and the reorder controls.
- [ ] `/admin/hero/[id]` edits eyebrow, title, subtitle, image, CTA label, CTA href, `is_hidden`. Create redirects into the editor, as `createProductAction` does.
- [ ] **Images reuse the `product-images` bucket** under a `hero/` prefix. No migration, no new policy: `product_images_storage_admin_write` is `bucket_id = 'product-images' and private.is_admin()`, which already covers it. The bucket's name is mildly wrong for the contents; a second bucket is a migration, two policies and an `rls.mjs` section to fix a noun.
- [ ] Generalise the uploader minimally — `pathPrefix`, and `hiddenFields: Record<string, string>` replacing the two Product-shaped props. Two copies of a Storage upload is how one of them keeps `upsert: false` and the other does not.
- [ ] **Ordering is dense and unique as a *result*, not a constraint.** Every reorder rewrites the list to `0…n-1`. Arrows are "move to position ±1"; the number box is "move to position N, everything from N onward shifts down". Both call one action with a different argument.
  - Do **not** add a unique index on `sort_order`. `20260919120000_product_images.sql:34` rejected exactly that, for a mechanical reason that still holds: supabase-js sends each `UPDATE` in its own transaction, so any swap passes through a duplicate, and a unique index turns that into a failed write plus a temp-value dance.
  - `ponytail:` the renumber is N sequential updates, non-atomic. At a handful of rows edited by one person the worst outcome is a list that is still totally ordered, because ties break on `created_at`. Upgrade path if it ever matters: one `reorder_hero_stories(uuid[])` RPC doing it in a single statement.
- [ ] Extract `reorderIds(ids, id, toIndex)` into `lib/admin-hero.ts` as a pure function with **one vitest file**. CLAUDE.md exempts this step from required TDD, but this is the only part of step 4 that can be wrong invisibly — off-by-one at either end of the list.
- [ ] Half-filled CTAs **warn and save**. The schema allows a label with no href and `components/HeroStory.tsx` degrades to a Story with no button; an editor that refuses to save cannot hold a half-drafted row.
- [ ] Delete is a plain button under the "Hide it instead" copy the Products editor carries, behind `ConfirmSubmitButton`. Nothing references a Hero Story, so unlike a sold Product the database will not save the client from a misclick.
- [ ] Use `ConfirmSubmitButton` on the Product, Variant and image deletes too. One import per site; Product delete is the one with the worst blast radius.
- [ ] `getHeroStories()` gains `.eq("is_hidden", false)` per the 2026-09-22 amendment to ADR 0003, and the docblock explaining admin-sees-Archive is **rewritten, not deleted** — someone who knows the Hidden-Product pattern will otherwise "fix" the filter back.
- [ ] `app/page.tsx` already handles every Story being Hidden (`f88f599`). Do not re-solve it; it now also covers "all Hidden *and* an admin is looking".

**Verify:** create a Story with an uploaded image entirely in the dashboard and see it on `/` · reorder with both controls and watch the numbers stay `0…n-1` · hide it and confirm it is gone from `/` **while signed in as the admin** · `npx vitest run` green including the new file · `npm run lint` 0/0.
