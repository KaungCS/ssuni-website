### #30 — reservation release (PR #61)

**The load-bearing half was already built and nobody had noticed.** `variants_available` and
`reserve_cart` have filtered on `expires_at > now()` since week 1, and `supabase/tests/rls.mjs`
section 6 has asserted it since #3. The issue's *Done when* — "held stock becomes purchasable again
after expiry **with the release webhook disabled**" — passed against `main` before this PR existed.

So #30 reduced to bookkeeping: a `checkout.session.expired` branch that sets `status = 'released'`.
One UPDATE, no RPC — `reserve_cart` and `complete_checkout` are Postgres functions because each is
several writes supabase-js cannot wrap in a transaction, and that reason does not apply to a single
statement.

**The `status = 'held'` predicate is the only safety in it.** Without it a replayed event would
rewrite a Reservation a payment already consumed, and that row is the frozen record of what an
Order's lines cost (#17). `rls.mjs` section 11 seeds a `held` and a `consumed` Reservation and
asserts the release takes the first, spares the second, and no-ops on replay.

**No sweep job was built.** The issue mentions one; ADR 0010 calls it housekeeping rather than
load-bearing, and `expires_at` in the past already says everything a sweep would write. Add it when
the table is big enough that the client complains, not before.

### #20 — `/profile` (PR #62)

`/profile` (list) and `/profile/orders/[id]` (full receipt). The detail route exists because Kaung
wants the surface a cancel, a return request or a review hangs off later — **none of those are
built**, and each is a real decision (does a cancel refund through Stripe? does it restock?) rather
than a button.

The Orders read moved into **`lib/orders.ts`**, and `app/checkout/success/page.tsx` was refactored
onto it. It had that embed inline with a comment naming `/profile` as the second caller and the point
where extracting paid, so this is the collection on that. Three callers, one `ORDER_SELECT`.

**The part to re-read if anything about Orders misbehaves:** `getMyOrders` filters on `user_id`
explicitly, and that is *not* redundant with RLS. `orders` carries `orders_select_own` **and**
`orders_admin_all` (#17), policies are OR'd, so for the admin account "whatever RLS returns" is every
customer's Orders. Delete that filter and `/profile` silently becomes an admin dashboard — for one
account, which is the worst way for it to break. `getOrderBySession` deliberately has no such filter;
`/checkout/success` is documented to lean on RLS alone.

### Honest note on the TDD gate

CLAUDE.md requires test-first for webhook handling, and `rls.mjs` section 11 was written before the

## Things that will bite you if you don't know them

**The Stripe endpoint must subscribe to two events, not one.** `checkout.session.completed` **and**
`checkout.session.expired`. `scripts/setup-stripe.sh` now prints the right `stripe listen --events`
line for local work; **the dashboard endpoint created in #26 must list the same pair**, or expired
Sessions leave `held` rows lying about forever. The route ignores everything else with a 200.

**`npm run db:verify` is now 60-odd checks across 11 sections and takes a while.** All green as of
this session, advisor reporting only the three documented findings (`rls_auto_enable` ×2, leaked
password protection). Sections 5, 6, 9 and 11 are the ADR 0010 chain; if you touch
`variants_available`, `reserve_cart` or `complete_checkout`, all four are the regression net.

**Both new `/profile` routes are `force-dynamic`**, like the catalog and `/checkout/success`. Order
Status changes while the shopper is not looking. Do not fold them into #41's caching work without
thinking about that.

**`lib/orders.ts` reaches `next/headers`**, exactly like `lib/catalog.ts`. A `"use client"` file
importing a runtime value from it fails the build. Type-only imports are fine.
